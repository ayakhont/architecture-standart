### <a name="_qmphm5d6rvi3"></a>**Решение**

**Общее описание:**
- Для описания MVP открытия депозита в интернет-банке представлена микросервисная архитектура без систем колл-центра,
чтобы не перегружать схему компонентами, не относящимися к задаче.
- В стороне вынесены компоненты мониторинга и логирования, которые будут использоваться для 
обеспечения надежности и поддержки системы (для контроля обеспечения требований Reliability+Performance+Supportability).
Я не стал их добавлять в системные рамки, чтобы не усложнять диаграмму.

**Описание решения:**
1. Интернет-банк задизайнен под микросервисную архитектуру с разворачиванием в Kubernetes.
2. Для взаимодействия интернет-банка с АБС используется Kafka.
3. Для реализации СМС-уведомлений используется внутренний СМС-шлюз банка (NotificationService).
4. Для обеспечения безопасности данных используется шифрование трафика.
5. Delphi-клиент АБС больше не ходит напрямую в Oracle, а работает через API. ABS Service не переносит логику, а только
оборачивает её вызывая PL/SQL процедуры через JDBC.
6. Для обеспечения масштабируемости интернет-банка используется горизонтальное масштабирование.

### <a name="_bjrr7veeh80c"></a>**Альтернативы**

Альтернативные решения:
1. Использование REST API вместо Kafka для взаимодействия интернет-банка с АБС.
   - Плюсы: проще в реализации и отладке, широко распространённый подход.
   - Минусы: может быть менее производительным при высоких нагрузках, сложнее обеспечить надёжность доставки сообщений.
   - Причина отклонения: Требования по производительности и надёжности, а также ограничение +R4.
2. Постепенная миграция логики из БД АБС в сервисы:
   - Плюсы: уменьшение нагрузки на БД, улучшение масштабируемости.
   - Минусы: требует значительных усилий по рефакторингу и тестированию.
   - Причина отклонения: MVP решение, нецелесообразно для начального этапа. 

**Недостатки, ограничения, риски**

- Масштабируемость АБС ограничена Oracle. Рано или поздно всё равно потребуется переносить бизнес-код из PL/SQL процедур.
- В микросервисной архитектуре транзакции становятся распределёнными. Требуется Saga/Outbox/идемпотентность.
При сбоях возможны «висящие состояния» (например, депозит создан, а уведомление не отправлено).
- Требуется настройка и поддержка Kafka, что добавляет сложности в инфраструктуру.
- Необходимо обеспечить защиту данных при межсервисных взаимодействиях, что требует дополнительных усилий по безопасности.
- Повышенные требования к инфранструктуре, нужны DevOps
- Единый API Gateway — точка отказа
